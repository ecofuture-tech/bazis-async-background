# bazis-async-background 2.3.0

Requires Bazis 2.3.1, bazis-ws 2.3 and FastStream 0.6 or newer.

## Security

- **Anonymous tokens could address user channels.** A token that is not a JWT was used as
  the channel name as is, so a client sending `Authorization: Bearer user_ws::42` received the
  status updates of user 42 and could read the results of his tasks. Anonymous channels are
  now the channels of bazis-ws 2.3 (`user_ws:anon:<token>`, tokens of 16–128 characters
  `A-Z a-z 0-9 _ -`).
- **The task id addressed any key of the cache database.** The statuses were stored under
  the bare task id, and `GET /async_background_response/{task_id}/` read whatever key it
  was given. They are now stored under `async_bg:task:<task_id>`; tasks queued before the
  upgrade are not found (their statuses expire after `KAFKA_RESPONSE_HOLD_SEC` anyway).
- The error of a failed publication is logged instead of returned to the client.

## Fixes

- **Consumers did not start with current FastStream**: the subscribers passed
  `auto_commit`, which FastStream 0.6 replaced with `ack_policy` and 0.7 removed. The new
  `subscriber_kwargs()` builds the arguments of a subscriber from the settings;
  `KAFKA_ENABLE_AUTO_COMMIT` maps to `AckPolicy.ACK_FIRST`, otherwise the new
  `KAFKA_ACK_POLICY` applies (`reject_on_error` by default).
- **A consumer without `KAFKA_CONSUMER_LIFETIME_SEC` failed at start** (`None + int`), and
  with it the lifetime had no effect: a timer slept and nothing stopped the application.
  The application now stops after its lifetime, and `kafka_consumer_multiple` starts a new
  process. Without Kafka settings the consumer command exits with an error.
- **Two requests publishing at the same time on a new event loop blocked it**: a threading
  lock was held across the start of the broker. One broker per event loop is started under
  an asyncio lock; `KAFKA_PUBLISH_TIMEOUT_SEC` (unused before) is the request timeout of the
  producer. The objects of closed event loops are released.
- **The result of a fast task could be lost**: the status `pending` was written after the
  publication returned and could overwrite `completed` written by the consumer meanwhile.
  A task is `pending` before it is published (the status `created` is no longer used).
- The statuses are written with the asyncio Redis client of bazis-ws instead of the single
  thread of `sync_to_async`.
- Brokers are kept per event loop object, not per `id()`; task modules can be imported
  without Kafka settings.
- An unknown task returns a JSON:API 404.

## Tests

The tests no longer require Docker: the API and the internals are tested without Kafka, and
the end-to-end test (marked `kafka`) runs when Kafka is configured. CI starts Kafka (KRaft),
a consumer and runs all of them on Python 3.12–3.14 and with the lowest allowed dependency
versions; releases are made with the Release workflow (see `CLAUDE.md`).
